# Klart — product and data model

Klart is a to-do app built around **My Day**: each morning you pull in what's due from ranked suggestions, then work through the list. Its whole state is plain JSON, so people, scripts and LLM agents can read and write it.

The design lives in the Klart canvas artifact (My Day, Settings, Notifications, quick-add syntax / JSON / LLMS.txt, mobile screens, icon). This document records how the web app implements it.

## Shopping and My Day

Shopping is a page of the main screen, not a separate one: it is the fifth row under the smart views (with how many items are left), and picking it keeps the sidebar and swaps My Day's list, Suggestions and editor for the lists column and the selected list. Picking a smart view or a tag goes back to My Day.

The sun on an item makes it a task in today's My Day (`Buy: Milk × 2`), in the list's context. The task carries `shopping: { listId, itemId }` and the item carries the task's id in `taskId`. The data format also allows a task for a whole list (`itemId: null`, the list's `taskId`), e.g. one an agent adds; the app doesn't create one.

Agents learn the list format and every shopping job (add, buy, star, put in My Day, complete, move, rename, delete) from the "Shopping lists" section of `LLMS.txt` (`core/sync/LlmsTxt.ts`), and read what's left to buy from the generated `views/shopping.json` (`buildShoppingView` in `core/tasks/AgentViews.ts`). Keep both in step with `core/shopping/` when the model changes.

- Item to task: the shopping mutations in `ShoppingData.ts` update the linked task with the same timestamp: buying completes it, starring stars it, editing the name or quantity retitles it, editing the note or link updates its notes and links, removing the item or pressing the sun again archives it.
- Task to item: `reconcileShoppingTasks()` runs after every mutation (in `useKlartActions` and `useShoppingActions`) and after each sync pull. A linked task newer than its item sets the item's `bought` and `important`; an archived task unlinks it. A task never undoes a newer change made on the list.
- In My Day a linked task shows its list's name with a cart icon, and opening it goes to the list (`/shopping?list=<id>`). Completing a list completes its own task; items moved to another list keep their tasks, items left behind have theirs archived.
- On phones the Shopping page shows the lists, then one list. Shopping is one history entry like a smart view, so Back from any list returns to My Day.

## Storage and sync

- Data is always persisted in the browser (`localStorage` key `klart-data`).
- **Folder sync** (Settings → Sync): the user picks a folder (e.g. inside OneDrive or iCloud Drive) with the File System Access API — Chrome/Edge on desktop. The handle is kept in IndexedDB; after a browser restart the user clicks "Reconnect" to re-grant access.
- `FolderSync` pulls every 4 s (when visible) and on focus, and pushes 400 ms after a change. It only reads files whose `lastModified` changed and only writes files whose content changed.
- Upgrades: files are parsed leniently and compared with what the current version would write, so after an update the first push rewrites `LLMS.txt` and any task, day or config file in an older format (without touching `updatedAt`). Browser data is normalized the same way on read.
- Data version (`core/sync/DataVersion.ts`): the app's `major.minor` (patch releases never change the files). Every push writes it to the folder's `klart.json` as `dataVersion`, so a folder records the newest version that wrote to it. An app whose data version is older stops pulling and pushing that sync (state `outdated`; `FolderSync` throws `NewerDataVersionError` before reading or writing anything), so it never half-reads newer files or writes over them in an older format. Local edits stay in the browser and sync after the update. A toast (`useOutdatedSyncNotice`) and the sidebar card say which version is needed; in the web app "Update" (`core/pwa/UpdateApp.ts`) fetches the newest service worker and reloads, while the desktop app asks for a new install. A folder without `dataVersion` (written before this existed) syncs as before. Versions from before this check can't be stopped and drop the field when they write `klart.json`; the next newer push restores it. The desktop Git sync checks the remote's `klart.json` right after fetching, before it commits, merges or pushes anything (`git_sync` fails with `newer-data-version:<version>`, read by `readNewerDataVersionError`), and a merge conflict in `klart.json` keeps the side with the newer `dataVersion`. A release that changes how files are written or which folder holds what must be a minor (or major) release, so the versions before it stop syncing.
- Conflicts: newest `updatedAt` wins per task; a losing remote edit is copied to `.conflicts/`. On first connect, local and folder data are merged.
- **Removals survive restarts** (`SyncBase`, `syncBasesAtom`, localStorage `klart-sync-bases`): after every pull and push a device keeps, per sync, the context ids the folder's `klart.json` listed and the task and list ids it held with their `updatedAt`. That's the common ancestor: a task or list the folder held and no longer does was removed by another device (or a person in the Git repo), so it's removed here too instead of written back, unless it was edited here after the version the folder held. A file the folder never had is new here and is written. The base is tied to the sync's connection; pointing a sync somewhere else or removing it starts over.
- **Read before write.** Every push pulls first, in the same job, so a file another device changed since the last pull is merged by `updatedAt` instead of overwritten. Jobs from every tab and window of the app take turns through a Web Lock (`klart-sync`), on top of the one in-tab queue. Across devices, Git and GitHub already reject a push that isn't based on the newest commit (the sync merges and retries), which is the real lock; a plain cloud folder can't be locked reliably, so it relies on the read-before-write and the rules below.
- **A folder is never emptied.** A push never writes a `klart.json` without contexts over one that has some, and a folder that listed contexts last time but now has no `klart.json`, or one that lists none, stops the sync with an error (`EmptiedFolderError`) until someone restores it, instead of every device treating its contexts as removed.
- Folder layout, matching LLMS.txt:

```
Klart/
├── LLMS.txt                  # rules for agents (optional)
├── klart.json                # contexts
├── tasks/<context>/<id>.json
├── days/YYYY-MM-DD.json
├── lists/<id>.json           # shopping lists, newest updatedAt wins per list
├── views/today.json          # generated, read-only (optional)
├── views/suggestions.json    # generated, read-only (optional)
├── views/shopping.json       # generated, read-only (optional): open lists, items left
├── inbox/                    # .txt (quick-add lines) or .json tasks; consumed and deleted
├── requests/                 # automation request files; the handler deletes them, Klart never reads them
├── devices/<name>/device.json
└── .conflicts/
```

- **GitHub sync** (Settings → Sync → GitHub): works in every browser, including phones, and in the desktop app. See [GitHub sync](#github-sync).

### Several syncs

Most people have one sync, and every context syncs with it. A device can also have several named syncs ("Personal repo", "Work OneDrive"), each a folder, Git clone or GitHub repository. A context lives in the sync it was created in (or that it was found in) and can't be moved to another one; a context with no sync is kept on this device only. The model lives in `core/sync/SyncTargets.ts`. The setup (`SyncSetup`: the syncs and a context-to-sync map) is per device, in `localStorage` (`klart-sync-targets`). GitHub tokens are stored there too, and each browser folder's handle is kept in IndexedDB under its sync's id. The older single-connection keys (`klart-github-connection`, `klart-desktop-connection` and the `data-folder` handle) are moved into it on first start.

- The first sync is the **primary**. Contexts nobody assigned sync with it. Shopping lists sync with their context's sync. Settings → Sync shows one card per sync (rename, make primary, stop syncing) with the contexts that live in it, and "Add another sync"; it can't move a context.
- Settings → Contexts lists every context from every sync, each card naming the sync it lives in ("This device only" when none). With several syncs, "New context" has a picker for the sync it goes to (`placeNewContext`); the primary is the default. Contexts can be reordered and hidden there as before.
- **Hidden contexts** are per device (`localStorage` key `klart-hidden-contexts`, `hiddenContextIdsAtom`) and keep syncing. Screens read `visibleKlartDataAtom` (`withoutHiddenContexts`), which leaves out the hidden contexts with their tasks, My Day items and lists, so they're gone from the switcher, ⌥ shortcuts, All contexts, Shopping, quick-add routing and notifications. The last shown context can't be hidden.
- Each sync's folder only holds its part (`FolderSync` with a `SyncScope`, see `scopeData`): its contexts in `klart.json`, their task and list files, and the My Day items of their tasks. A pull replaces only that part (`mergeOwned`), so the other syncs' contexts and My Day items are kept. A task or list file that no longer belongs to a folder is removed.
- **The folder decides, not the device.** Which contexts a folder holds comes from its own `klart.json` (`getSyncScope` with the `SyncListings`: each sync's listed context ids as last read or written, `syncListingsAtom`). A context listed there stays there whatever this device's setup says, so two devices whose setups disagree can't take contexts out of each other's folders. A context listed in no folder goes into a folder only when it was created on this device (`placeNewContext` records it in `pendingContexts` until a folder lists it), into the sync it's assigned to or the primary, and only once every sync has been read since the app started, so an out-of-date assignment never copies a context into a second folder. The first sync a device connects also takes the device's existing contexts on its first read (`adoptLocalContexts`): all of them for an empty folder, only those with tasks or lists for a folder in use. Nothing is pushed to a folder before it has been read.
- **A pull never removes a context.** One that left a folder may have moved to another sync, so it stays while any sync lists it, and keeps being written to the folder that does. Once every sync has been read, contexts no folder lists that weren't created here and aren't kept on this device on purpose are out of date (removed elsewhere, or moved to a sync this device doesn't have): they're dropped from this device with their tasks, lists and My Day items (`findStaleContexts`, `withoutContexts`), never written back. A copy of what was dropped is kept in localStorage (`klart-dropped-contexts`, last 10). A device whose folders all list nothing keeps its contexts.
- Contexts found in a sync's `klart.json` are assigned to that sync (`assignFoundContexts`), which is how a device learns where every context lives and what Settings shows. A context assigned to another sync stays there while that sync lists it too (or hasn't been read yet); an assignment its own folder doesn't back up is out of date and moves. That includes contexts kept on this device, so reconnecting a sync picks its contexts up again, and contexts assigned to a sync that was removed. Stopping a sync keeps its contexts on this device instead of moving them into another sync. Making another sync primary keeps the old primary's contexts where they are.
- `FolderSyncLifecycle` mounts one runner per sync (`useSyncTargetLifecycle`). All runners share one job queue and read the latest data when a job starts, so two syncs never pull over each other. Each sync has its own status (`syncStatusesAtom`). The sidebar card (`SyncStatusCard`, from `buildSyncOverview`) shows the worst state across syncs and, when contexts are split, one row per sync with its state and context dots.

## Notifications

`NotificationPlanner.planNotifications()` is pure and decides what is due: task reminders (`remindAt`), "Plan your day", "Due today without a time", "Overdue nudge" and "End of day wrap-up", each within its time window and the context's hours. The scheduler runs every 20 s while the app is open, shows system notifications when permission is granted (via the service worker when registered) and in-app toasts otherwise. Sent keys are remembered per device. With several devices, the "last used" policy uses `devices/*/device.json`.

## What's new

After an update (a new PWA bundle or desktop build with a higher `version` in `apps/web/package.json`), Klart shows a "What's new" dialog once with the release notes in `core/whats-new/ReleaseNotes.ts`. The last version seen is kept per device in `localStorage` (`klart-last-seen-version`). A fresh install shows nothing; a device that already had data but no last-seen version gets the latest notes once. Settings → About → "See what's new" reopens it.

To ship notes: bump the version and add an entry at the top of `RELEASE_NOTES` — a few emoji highlights, plus only the fixes people would notice. Versions without an entry are skipped quietly. `/bump-version` (or `/bump-patch`, `/bump-minor`, `/bump-major`) does both: `scripts/bump-version.mjs` keeps the root and `apps/*` `package.json` files, `Cargo.toml` and `Cargo.lock` in sync, and `/add-release-notes` writes the entry.

## Desktop app

`apps/desktop` packages `apps/web/dist` with Tauri 2 (see CLAUDE.md for commands). The web code detects it with `isDesktop()` (`core/platform/Desktop.ts`) and calls native commands from `apps/desktop/src-tauri/src`:

| Feature                                                   | Browser                                                           | Desktop app                                                                                                   |
| --------------------------------------------------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Folder sync (OneDrive, iCloud Drive, Dropbox, any folder) | File System Access API, Chrome/Edge only (`BrowserFolderBackend`) | Native file commands, every OS (`DesktopFolderBackend` → `folder.rs`); writes are atomic (temp file + rename) |
| Git sync                                                  | —                                                                 | `git.rs`, using the installed `git` and the user's SSH keys / credential helper                               |
| GitHub sync                                               | GitHub REST API (`GitHubBackend`)                                 | Same as the browser                                                                                           |
| Notifications                                             | Web Notifications / service worker                                | Native, via `tauri-plugin-notification` (`system.rs`)                                                         |

Task links use `target="_blank"`, which the webview ignores, so `useDesktopExternalLinks()` sends those clicks to `open_url` (`system.rs`) and the default browser.

`FolderSync` only talks to the `FolderBackend` interface, so both platforms share the sync logic.

### Automations

Settings → Automations is off by default. Saved automations are read-only rows (name, kind, command or URL, Enabled switch); **Edit** opens a draft that only lands on **Save**, so a name never changes by itself, which matters because request-file handlers match on it. Turning it on shows a **Run** button in the My Day header. The button runs every enabled automation in parallel, then asks for a sync so whatever the automations wrote gets pulled in. With more than one automation, a chevron beside the button runs a single one. The command palette (⌘K) has the same entries under "Automations": "Run <name>" for each one, plus "Run all automations" when there are several. The model is in `core/automations/`, and `useAutomations()` runs them. There are three kinds:

- **Shell command** (desktop app only; skipped in a browser): `run_command` (`automation.rs`) runs it in the user's login shell (`$SHELL -lc`, `cmd /C` on Windows), so a GUI app gets the user's PATH. It runs in the primary sync's folder when that sync is a desktop folder or Git clone. A non-zero exit code counts as a failure, and the last line of stderr shows in the toast.
- **Webhook**: a `POST` with `{ source, automation, date, device }` as JSON, plus any headers the user set (e.g. a GitHub token for `workflow_dispatch`). In a browser the server must allow CORS.
- **Request file**: queued in `pendingRequestsAtom` and written to `requests/` by the primary sync's next push (`FolderSync.writeRequests`), so with Git or GitHub it's committed along with that push. A watcher or GitHub Action reacts to the file and deletes it. `/add-request-handler` sets one up for macOS, Linux, Windows or GitHub Actions.

Automations are stored per device in `localStorage` (`klart-automations`) and never synced, so a shared folder or repository can't plant commands that run on someone else's computer.

### Git sync

The data folder is a local clone. Settings → Sync → Git repository either clones a URL into a folder you pick or uses an existing clone. Each sync (`git_sync`):

1. commits local changes (`klart: 3 tasks updated`),
2. fetches and merges the remote; a conflicting file keeps the version with the newer `updatedAt`, and the other version is committed to `.conflicts/`,
3. pushes.

It runs when the app opens, every 5 minutes, 30 seconds after the last local change, and on "Sync now". After a merge that brought changes, the folder is re-read immediately. `GIT_TERMINAL_PROMPT=0` makes git fail instead of waiting for a password; the error shows in Settings. Without `user.email` configured, commits use `Klart <klart@localhost>`.

### GitHub sync

For phones and browsers without folder access. The user enters a GitHub username, a repository and a fine-grained personal access token (GitHub's API doesn't accept passwords) limited to that repository with Contents: Read and write. Only private repositories are accepted, and the token can't be read-only. The connection, token included, is kept in `localStorage` (in the sync setup, `klart-sync-targets`) on that device only.

`GitHubBackend` implements `FolderBackend` over an in-memory snapshot of the default branch, so `FolderSync` runs unchanged:

- `refresh()` checks the branch (an `If-None-Match` request; unchanged costs nothing against the rate limit), and on a new commit loads its tree and downloads changed files, 6 at a time. A file's git blob sha stands in for `lastModified`.
- Writes and removals are staged in memory. `commit()` pushes them as one commit through the Git Data API (tree → commit → fast-forward the branch). An empty repository gets its first file through the contents API.
- When another device pushed first, the branch update is rejected: the sync refreshes, drops staged files that changed remotely, pulls (merging by `updatedAt`, losers to `.conflicts/`), pushes and commits again, up to 3 times.

It syncs when the app opens, every minute while visible, 5 seconds after the last change, when the app is hidden with unpushed changes, and on "Sync now". With a Git or GitHub remote, device check-ins (`devices/*/device.json`) are only written alongside real changes, so they never make a commit of their own. A GitHub-synced device and a desktop Git clone can share the same repository.

Not yet built: the online OneDrive API (for computers without the OneDrive app), "Sign in with GitHub" (GitHub's OAuth endpoints don't allow browser calls, so it needs a small server), and the design's desktop-only items (menu-bar mode, open at login, notification actions).
